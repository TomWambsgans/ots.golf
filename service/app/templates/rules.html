Rules

How cheaply can a hash-based one-time signature be verified?

An upper bound constructs a scheme that never exceeds the claimed cost. A lower bound proves that every admissible scheme in a chosen class has worst-case cost at least as large. Every claim needs a Lean-kernel-checked proof.

Three lower-bound frameworks

Each class has its own lower record. A restricted result does not establish the same bound for a broader class.

1. Generic algorithms

Arbitrary terminating oracle programs for key generation, signing and verification. No required graph, disclosure pattern or nonce format. Honest signatures must verify, and signing must succeed with probability at least 1/2 for every message-selection rule based on the public key. This availability threshold is fixed for generic lower submissions.

2. DAGs

A fixed, public, directed acyclic graph of secret random sources, deterministic operations and hashes, with unrestricted sharing. The public key is the low 128 bits of its root hash. A signature reveals a cut: node values meeting every source-to-root path, excluding the root. Verification reconstructs the root forwards.

3. Partial disclosures

DAGs with at most 46 distinct hash origins per signature payload. Trace disclosed values backwards through deterministic nodes, stopping at hashes; count distinct hash nodes reached. Sources count zero; every declared parent edge counts.

Fragments and encodings, including Reed–Solomon symbols, are allowed. Fragments of one hash node count once; values from two hash nodes count twice, even if equal. The cut and forward reconstruction rules still apply, without arbitrary decoding from selected symbols.

DAG signature format. A message-and-nonce hash selects the cut.

The low 128 bits of H(message ‖ nonce) select one of 2115 fixed cuts. Signing tries at most 221 fresh 256-bit nonces for an in-range index, otherwise it fails. The signature contains the nonce and at most 5,248 payload bits. Verification pays for the index query and reconstructed hashes; its cost is maximized over all cuts.

One upper track: generic algorithms

Submit any oracle algorithm. Prove that honest signatures verify, signing succeeds with the required probability, and security, size and resource bounds hold. The claimed verification cost must cover every input and execution path, including rejection. There is no DAG or disclosure restriction.

How to submit

Open: generic lower, DAG lower and partial-disclosure lower. Pending: generic upper, until its admissibility requirements and signing-failure allowance are pinned.

  1. Fork the repository. Change only formal/Submissions/GenericLower/, formal/Submissions/Lower/ or formal/Submissions/DisclosureLower/.
  2. Put your integer claim in claim.txt and export the required declarations from Solution.lean. Follow the exact submission requirements.
  3. Run python3 verifier/verify.py lower --source . (or generic-lower or disclosure-lower), then open a pull request. A verified strict improvement is merged and becomes the record.

No sorry or extra axioms: only {{ cfg.permitted_axioms|join(', ')|safe }}. Verification has {{ cfg.limits.wall_clock_seconds // 60 }} minutes and {{ cfg.limits.memory_bytes // 1073741824 }} GiB. The generic contract, DAG contract, disclosure condition and verifier configuration define the exact requirements.
