Rules

What is a one-time signature?

A digital signature lets someone prove that they approved a message. The signer keeps a secret key and shares a public key. Anyone with the public key can check a signature, but should not be able to create one for a different message.

A one-time signature protects one signing request per key pair. After observing that signature, an attacker should still be unable to forge one on another message. Signing a second message with the same key is outside the security guarantee.

Here, schemes use hashing as their only cryptographic primitive. The question is how much hashing a verifier must do to check a signature.

What do upper and lower bounds tell us?

An upper bound gives a construction: prove that your scheme never exceeds the claimed verification cost. A smaller upper bound means a cheaper construction.

A lower bound proves a limit: every admissible scheme in the chosen class has worst-case verification cost at least as large as your claim. A larger lower bound rules out more ambitious cost targets.

Both require a Lean-kernel-checked proof. An example, benchmark or numerical search is not enough: the claim must hold for all inputs and cases covered by its formal statement.

Which lower-bound frameworks can I use?

Three lower-bound frameworks let you ask the question at different levels of generality. Each class has its own lower record:

  • Generic algorithms allow arbitrary oracle programs.
  • DAGs fix a computation graph and reveal a cut through it.
  • Whole words further restrict those graphs to hashing, selecting hash halves and concatenating complete 128-bit words.

A lower bound for a restricted class does not establish the same bound for a broader class. The three frameworks apply only to lower bounds; the single upper track is generic.

Generic algorithms: what is allowed?

Any terminating oracle programs for key generation, signing and verification. Private randomness and adaptive oracle queries are allowed. There is no required graph, disclosure pattern or nonce format.

Honest signatures must verify. For every message-selection rule based on the public key, signing must succeed with probability at least 1/2, averaged over honest key generation and signing. This availability threshold is fixed for generic lower submissions. It is not a per-key guarantee or a guarantee after adversarial oracle queries.

The scheme supplies an injective bit-string encoding: different signatures have different encodings. Every signature the signer can return fits in 5,504 bits, and the verifier always rejects oversized encodings. Honest signing and verification share the same oracle; a returned honest signature is rejected with probability zero.

Cost bounds hold on every execution path. Signing is bounded for every secret key and message; verification for every public key, message and signature, including rejection. A lower claim rules out every smaller verification budget that covers all these cases.

DAGs: how does revealing a cut work?

A directed acyclic graph (DAG) describes a computation with no loops. Its nodes are secret random sources, deterministic operations or hashes. Its structure, node lengths and deterministic functions are public and fixed. Values may be shared by several later nodes.

The sources are independent uniform bit strings of fixed lengths. Each deterministic node uses only its declared parents; each hash node hashes one parent's entire value. Concatenation and other encodings are deterministic operations. Parents precede children.

Key generation evaluates every node once and stores all values as the secret key. The public key is the low 128 bits of the root hash. A signature reveals a cut: stored node values that meet every source-to-root path, without revealing the root.

The verifier walks backwards from the root along every declared parent edge, stopping at the disclosed values. It then evaluates the required nodes forwards, once each. No undisclosed source may remain on a required path.

DAG signing: how is the cut chosen?

The scheme supplies 2115 indexed cuts; cuts may repeat. The message and a random nonce select one: read the low 128 bits of H(message ‖ nonce) as an integer. It is a valid index when below 2115.

Signing tries up to 221 uniformly sampled 256-bit nonces without replacement. It stops at the first valid index, otherwise it fails. The signature contains that nonce followed by the cut's node values, in node order, with at most 5,248 payload bits.

Verification rejects an invalid index or a payload of the wrong length. Otherwise it reconstructs the root and compares its low 128 bits with the public key.

The cost is one compression for the message-and-nonce query, plus the costs of all reconstructed hash nodes. The score is the maximum over every indexed cut, even one that is unlikely to be selected.

Whole words: which operations are allowed?

This class uses the same DAG rules, with values built from whole 128-bit words. Each source is an independent uniform 128-bit word. A hash returns 256 bits, usable as two 128-bit halves.

A deterministic node either selects the fixed low or high half directly from a hash node, or concatenates earlier node values. Those values may contain several words. Concatenation may reorder or repeat values, and may be empty. No other deterministic operation is allowed: no smaller bit fragments, XOR, encoding or nonempty constant nodes. Sharing remains unrestricted.

A signature discloses complete node values, which may group several words. The 5,248-bit payload fits at most 41 words, plus the usual 256-bit nonce. Disclosed nodes still form a cut.

Hash inputs may concatenate any number of words. Hashing n words costs max(1, ⌈n / 4⌉) compressions: four words fit in one block, and an empty input still costs one compression. The existing cost budgets apply; there is no fixed input arity.

What must an upper-bound construction prove?

One upper track: generic algorithms. Submit any oracle algorithm, with no required DAG or disclosure pattern.

Prove that honest signatures verify, signing succeeds with the required probability, and strong security, size and resource bounds hold. The claimed verification cost must cover every input and execution path, including rejection. The exact admissibility requirements and signing-failure allowance must be pinned before this track opens.

Legacy DAG upper certificates remain available as references, including Historical partial disclosures. They are not certificates for the whole-word class or the generic upper track. Their submission roots are closed.

How do I submit a proof?

Open: generic lower, DAG lower and whole-word lower. Pending: generic upper, until its admissibility requirements and signing-failure allowance are pinned.

  1. Fork the repository. Change only formal/Submissions/GenericLower/, formal/Submissions/Lower/ or formal/Submissions/DisclosureLower/.
  2. Put your integer claim in claim.txt and export the required declarations from Solution.lean. Follow the exact submission requirements.
  3. Run python3 verifier/verify.py lower --source . (or generic-lower or disclosure-lower), then open a pull request. A verified strict improvement is merged and becomes the record.

The pull request supplies your attribution and description. Optional Assisted by: and Co-authors: lines credit collaborators. Updating the PR queues its new head for verification; merging the verified improvement promotes it to a record.

What does the verifier check?

Use one flat root: identifier-named .lean files, claim.txt, and an optional README.md. Solution.lean is required. The claim is a non-negative integer without leading zeros, at most {{ cfg.limits.max_claim|int }}, with at most one trailing newline. The verifier inserts it into the exact theorem statement.

Import only Mathlib, VCVio, your track's permitted contract modules and sibling files. Protected definitions cannot be changed by a submission. Use the pinned Lean toolchain and dependency manifest. Limits: {{ cfg.limits.max_files }} files, {{ cfg.limits.max_file_bytes // 1048576 }} MiB per file and {{ cfg.limits.max_total_bytes // 1048576 }} MiB total.

No sorry or extra axioms: only {{ cfg.permitted_axioms|join(', ')|safe }}. native_decide introduces an unpermitted axiom. The exported declarations must match the rendered challenge exactly. Verification runs without network access, with {{ cfg.limits.wall_clock_seconds // 60 }} minutes and {{ cfg.limits.memory_bytes // 1073741824 }} GiB.

The generic interface, generic lower statement, DAG contract, whole-word condition and verifier configuration define the exact requirements. See the full submission specification for the permitted imports and file rules.
