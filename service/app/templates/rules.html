Rules

What is a one-time signature?

A one-time signature (OTS) uses a key pair to sign one message securely. For examples, see Lamport signatures, which reveal selected secrets, and Winternitz signatures (WOTS+), which use hash chains.

What are we optimizing?

A one-time signature scheme has public-key and signature sizes, a security level, and costs for key generation, signing and verification. We measure those costs in hash compressions. We fix the following requirements and ask how few compressions verification can require in the worst case.

Fixed requirements and the verification objective
ParameterRequirement
Public key128 bits
Message256 bits
SignatureAt most 5,504 bits
Key generationAt most 1,024 compressions
SigningAt most 221 compressions
Security127 bits
VerificationMinimize worst-case compressions

There are two tracks, both requiring a Lean-kernel-checked proof:

  • Upper bound. Construct a provably secure OTS using as few verification compressions as possible, and prove its worst-case cost is at most the claim. Any oracle algorithm is allowed; it must also meet the correctness, signing availability and resource requirements below. Smaller claims are better.
  • Lower bound. Prove that every admissible OTS in a chosen class needs at least the claimed worst-case verification cost. Larger claims are better.

A lower bound for all possible algorithms is difficult to prove. The lower track therefore offers three levels of generality, each with its own record:

  • Generality 3/3. Any oracle algorithm.
  • Generality 2/3. A fixed DAG with arbitrary deterministic functions.
  • Generality 1/3. DAGs built from whole 128-bit words, hashes, hash halves and concatenation.

Upper bound and Generality 3/3 lower bound: any algorithm

A scheme consists of three terminating oracle programs: key generation, signing and verification. They may use private randomness and adaptive queries. Whenever honest signing returns a signature, verification accepts with probability one. For every message chosen as a function of the public key, signing failure is at most 2−128 in both tracks. This probability averages over honest key generation and signing, starting from a fresh oracle.

Signature encodings must be lossless. Every possible signer output fits in 5,504 bits; oversized signatures are always rejected. Cost bounds hold on every path: signing for every secret key and message, verification for every public key, message and signature, including rejection. A lower claim rules out every smaller budget covering all these cases.

Lower bound · Generality 2/3: DAGs

The scheme fixes a public directed acyclic graph (DAG), its value lengths and its node functions. Sources are independent uniform bit strings; deterministic nodes apply arbitrary functions to their declared parents; hash nodes hash one parent's entire value. Parents precede children, and each value may feed multiple nodes. Key generation evaluates every node once and stores all values. The public key is the low 128 bits of the root hash.

A signature reveals a cut: stored values meeting every source-to-root path, excluding the root. Verification follows all declared parent edges backwards to the cut, then evaluates required nodes forwards, once each.

  1. Select a cut. The scheme supplies 2115 indexed cuts, possibly repeated. Read the low 128 bits of H(message ‖ nonce) as an integer; it is valid below 2115. Try up to 221 uniformly sampled 256-bit nonces without replacement, stopping at the first valid index or failing.
  2. Reveal. Send the nonce and the cut's node values in node order, with at most 5,248 payload bits.
  3. Verify. Reject invalid indices or wrong payload lengths; otherwise reconstruct the root and compare its low 128 bits with the public key.

The score is the maximum over all indexed cuts: one compression for the message-and-nonce query, plus the costs of reconstructed hash nodes.

Lower bound · Generality 1/3: whole words

These DAGs use whole 128-bit words. Each source is one independent uniform word; each hash returns 256 bits. Each deterministic node performs one of two operations: select a fixed low or high half directly from a hash output, or concatenate complete earlier values. Concatenation may reorder, repeat, group or be empty; each value may feed multiple nodes.

Disclosures still form cuts and reveal complete node values. The 5,248-bit payload fits at most 41 words, plus the 256-bit nonce. A hash accepts any number of words: n words cost max(1, ⌈n / 4⌉) compressions. The same DAG signing, verification and cost budgets apply.

How do I submit a proof?

{% if generic_upper_track %}Submit an upper-bound construction, or a lower-bound proof for one of the three classes.{% else %}Submit a lower-bound proof for one of the three classes. Pending: the upper-bound track, until its challenge is pinned.{% endif %}

  1. Fork the submissions repository and follow its setup instructions. Change only formal/Submissions/GenericLower/, formal/Submissions/Lower/, formal/Submissions/DisclosureLower/{% if generic_upper_track %} or formal/Submissions/GenericUpper/{% endif %}.
  2. Put your claim in claim.txt and export the required declarations from Solution.lean.
  3. Run python3 .contract/verifier/verify.py lower --source . (or generic-lower, disclosure-lower{% if generic_upper_track %} or generic-upper{% endif %}), then open a pull request to the submissions repository. Its author and description supply attribution; optional Assisted by: and Co-authors: lines credit collaborators. Each new head is rechecked. A verified strict improvement becomes the record when merged.

What does the verifier check?

Use a flat root: identifier-named .lean files, claim.txt, optional README.md, and required Solution.lean. The claim is an integer from zero to {{ cfg.limits.max_claim|int }}, without leading zeros and with at most one trailing newline. Import only Mathlib, VCVio, permitted contract modules and siblings. Use the pinned toolchain and dependencies; submissions cannot alter protected definitions.

The verifier checks the exact claim and exported declarations. No sorry or extra axioms: only {{ cfg.permitted_axioms|join(', ')|safe }}. native_decide introduces an unpermitted axiom. Limits: {{ cfg.limits.max_files }} files, {{ cfg.limits.max_file_bytes // 1048576 }} MiB per file, {{ cfg.limits.max_total_bytes // 1048576 }} MiB total, {{ cfg.limits.wall_clock_seconds // 60 }} minutes, {{ cfg.limits.memory_bytes // 1073741824 }} GiB and no network.

The core repository defines the model and verifier: generic interface, generic lower statement, DAG contract, whole-word condition, verifier configuration and submission specification.
