Rules

What is a one-time signature?

A one-time signature uses a key pair to sign one message securely. For examples, see Lamport signatures, which reveal selected secrets, and Winternitz signatures (WOTS+), which use hash chains. These are background reading; this competition's model and limits are below.

What do upper and lower bounds tell us?

We seek the lowest worst-case verification cost. An upper bound constructs a secure scheme that never exceeds the claimed cost; smaller is better. A lower bound proves that every admissible scheme in a chosen class has worst-case cost at least as large; larger is better. Both require a Lean-kernel-checked proof.

Three lower-bound frameworks have separate records: generic algorithms, DAGs and whole words. A restricted result does not establish the same bound for a broader class. One upper track: generic algorithms. An upper construction must prove correctness, signing availability, strong security and all size and resource bounds, with no required DAG or disclosure pattern.

Legacy DAG and Historical partial disclosures upper certificates are references, not generic or whole-word certificates. Their submission roots are closed.

Generic algorithms: what is allowed?

Any terminating oracle programs, with private randomness and adaptive queries; no graph, disclosure pattern or nonce format is required. Honest signing and verification share the oracle, and returned signatures are rejected with probability zero. Signing succeeds with probability at least 1/2 for every public-key-dependent message choice, averaged over honest key generation and signing. This availability threshold is fixed for generic lower submissions. It is neither a per-key guarantee nor a guarantee after adversarial oracle queries.

Signature encodings must be injective: different signatures have different bit strings. Every possible signer output fits in 5,504 bits; oversized signatures are always rejected. Cost bounds hold on every path: signing for every secret key and message, verification for every public key, message and signature, including rejection. A lower claim rules out every smaller budget covering all these cases.

DAGs: how do signing and verification work?

A DAG is a fixed, public computation graph with no cycles. Sources are independent uniform bit strings of fixed lengths; deterministic nodes use only their declared parents; hash nodes hash one parent's entire value. Lengths and functions are fixed, parents precede children, and sharing is unrestricted. Key generation evaluates every node once and stores all values. The public key is the low 128 bits of the root hash.

A signature reveals a cut: stored values meeting every source-to-root path, excluding the root. Verification follows all declared parent edges backwards to the cut, then evaluates required nodes forwards, once each. No undisclosed source may remain on a required path.

{% include "_rules_cut_diagram.html" %}
  1. Select a cut. The scheme supplies 2115 indexed cuts, possibly repeated. Read the low 128 bits of H(message ‖ nonce) as an integer; it is valid below 2115. Try up to 221 uniformly sampled 256-bit nonces without replacement, stopping at the first valid index or failing.
  2. Reveal. Send the nonce and the cut's node values in node order, with at most 5,248 payload bits.
  3. Verify. Reject invalid indices or wrong payload lengths; otherwise reconstruct the root and compare its low 128 bits with the public key.

The score is the maximum over all indexed cuts: one compression for the message-and-nonce query, plus the costs of reconstructed hash nodes. Even rarely selected cuts count.

Whole words: which operations are allowed?

These DAGs use whole 128-bit words. Each source is one independent uniform word; each hash returns 256 bits. A deterministic node selects the fixed low or high half directly from a hash node, or concatenates earlier complete values. Concatenation may reorder, repeat, group or be empty; sharing is unrestricted. No other deterministic operation is allowed: no smaller fragments, XOR, encoding or nonempty constant nodes.

{% include "_rules_words_diagram.html" %}

Disclosures still form cuts and reveal complete node values. The 5,248-bit payload fits at most 41 words, plus the 256-bit nonce. Hash inputs have no fixed arity: n words cost max(1, ⌈n / 4⌉) compressions. The same DAG signing, verification and cost budgets apply.

How do I submit a proof?

Open: generic lower, DAG lower and whole-word lower. Pending: generic upper, until its admissibility requirements and signing-failure allowance are pinned.

  1. Fork the repository. Change only formal/Submissions/GenericLower/, formal/Submissions/Lower/ or formal/Submissions/DisclosureLower/.
  2. Put your claim in claim.txt and export the required declarations from Solution.lean.
  3. Run python3 verifier/verify.py lower --source . (or generic-lower or disclosure-lower), then open a pull request. Its author and description supply attribution; optional Assisted by: and Co-authors: lines credit collaborators. Each new head is rechecked. A verified strict improvement becomes the record when merged.

What does the verifier check?

Use a flat root: identifier-named .lean files, claim.txt, optional README.md, and required Solution.lean. The claim is an integer from zero to {{ cfg.limits.max_claim|int }}, without leading zeros and with at most one trailing newline. Import only Mathlib, VCVio, permitted contract modules and siblings. Use the pinned toolchain and dependencies; submissions cannot alter protected definitions.

The verifier checks the exact claim and exported declarations. No sorry or extra axioms: only {{ cfg.permitted_axioms|join(', ')|safe }}. native_decide introduces an unpermitted axiom. Limits: {{ cfg.limits.max_files }} files, {{ cfg.limits.max_file_bytes // 1048576 }} MiB per file, {{ cfg.limits.max_total_bytes // 1048576 }} MiB total, {{ cfg.limits.wall_clock_seconds // 60 }} minutes, {{ cfg.limits.memory_bytes // 1073741824 }} GiB and no network.
